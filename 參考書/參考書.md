# 前言：先把這個專案想成什麼

這個專案的核心不是一個普通網站，而是一套 **DDTank 4.1 遊戲伺服器與舊式 Flash 遊戲客戶端周邊程式**。

最簡單的想像方式是：

```text
玩家
  │
  ▼
Electron 客戶端
  │
  ├── 登入網站取得登入 Session
  │
  └── 取得 Flash / SWF 的位置
              │
              ▼
          Flash 遊戲客戶端
              │
              │ TCP 遊戲封包
              ▼
        Game.Server
              │
       ┌──────┴──────┐
       ▼             ▼
   遊戲世界         Center.Server
       │             │
       └──────┬──────┘
              ▼
          資料庫
```

這個圖不是一份「未來要做成什麼」的設計，而是閱讀目前程式最方便的總圖。

專案的 README 明確說明它是 DDTank 4.1 的開源伺服器基礎，目前仍在開發中；README 另外提出了一套放在 `app/` 下的現代化方向，但目前 `main` 分支的實際根目錄仍以舊有的 `Source Server`、`Web`、`ClientWeb`、`Db` 等內容為主。因此閱讀程式時，必須把「README 描述的方向」和「現在真的存在的程式」分開看。

# 第一章：專案現在到底有哪些東西

根目錄目前可以先分成幾大塊：

```text
DD/
├── ClientWeb/
├── Db/
├── Request/
├── Source Flash/
├── Source Server/
├── Tools/
├── Web/
├── README.md
├── package.json
└── pnpm-workspace.yaml
```

## 1.1 ClientWeb

這是 Electron 桌面客戶端。

它不是遊戲本體。它比較像一個「把舊 Flash 遊戲裝進桌面視窗裡」的外殼。

目前主要檔案有：

- `main.js`：Electron 的入口。
- `login.js`：負責呼叫網站登入 API、取得 Session，再取得遊戲 SWF。
- `public/`：Electron 內部使用的靜態網站內容。
- `flash/`：放 Flash Player 外掛的位置。
- `package.json`：定義 Electron、Express、Axios、MD5 等依賴。

## 1.2 Web

這是舊式網站部分。

裡面可以看到：

- PHP 頁面。
- ASP.NET `.aspx`。
- ASP.NET `.ashx` Handler。
- XML 設定。
- Flash 相關檔案。
- 圖片與網站資源。

例如：

- `index.php`：網站首頁。
- `play.php`：遊戲入口相關頁面。
- `checkuser.ashx`：玩家登入檢查入口。
- `LoginGame.aspx`：登入遊戲入口。
- `config.xml`：網站/遊戲相關設定。
- `crossdomain.xml`：Flash 跨網域存取設定。

## 1.3 Request

這裡是一大批舊網站 API / Handler。

檔名通常直接說明它做的事情，例如：

- `AccountRegister.ashx`：帳號註冊。
- `ActiveList.ashx`：活動資料。
- `AASGetState.aspx`：取得相關狀態。
- `AASUpdateState.aspx`：更新相關狀態。
- `AdvanceQuestTime.ashx`：任務時間相關操作。

它的特色是「一個 URL 對一個小功能」。很多 `.ashx` 檔案本身只是入口，真正的 C# 程式會在旁邊的 `.cs`。

## 1.4 Db

這裡放資料庫相關內容。

目前可以直接看到三份 SQL Server 備份：

- `Db_Membership_20200702.BAK`
- `Db_Tank41.BAK`
- `Db_Tank_20200702.BAK`

另外有：

```text
Db/Query/Reset all Server.sql
```

所以這個專案不是「只靠程式碼就能理解」；資料庫也是遊戲的一部分。

## 1.5 Source Flash

這裡是 Flash 原始碼相關資料，目前主要看到 `scripts/`。

README 特別把 `Source Flash/` 當成理解 Flash 客戶端流程、伺服器呼叫、封包格式與客戶端行為的重要參考來源。

## 1.6 Source Server

這是整個專案最重要的一塊。

它是舊 DDTank 伺服器端的 C# / .NET Framework 程式集合。

主要專案包含：

```text
AttRank
Bussiness
Center.Server
Center.Service
Fighting.Server
Fighting.Service
Game.Base
Game.Logic
Game.Server
Game.Server.Scripts
Road.Flash
Road.Service
SourceQuest4.5
SqlDataProvider
Tank.Request
libs
```

它不是「一個伺服器專案」，而是很多互相引用的小專案組合。

# 第二章：玩家從打開程式到進入遊戲

先不要看任何 C#。只看玩家的動作。

## 2.1 玩家打開桌面程式

`ClientWeb/main.js` 是 Electron 入口。

它做幾件很直白的事：

1. 載入 Electron。
2. 找到 `flash/pepflashplayer.dll`。
3. 把 Flash Player 外掛路徑交給 Electron。
4. 建立 Express 小型本機 HTTP 伺服器。
5. 開一個約 `1000 x 659` 的 Electron 視窗。
6. 視窗最後載入 `http://localhost:9284`。

所以玩家看到的畫面，本質上是：

```text
Electron 視窗
    ↓
本機 Express
    ↓
public/ 裡的網頁
    ↓
Flash Player
```

## 2.2 玩家按登入

Electron 用 IPC 把登入動作交給 `login.js`。

`login.js` 會先把玩家輸入的密碼做 MD5：

```text
玩家密碼
   ↓
MD5
   ↓
md5Pass
```

接著請求：

```text
/checkuser.ashx?username=...&password=...
```

成功後，它從 HTTP Response 的 Cookie 裡拿到 ASP Session。

這一步很重要：**登入成功不等於已經進入遊戲伺服器。**

目前這段程式先拿到的是網站登入狀態。

## 2.3 再用 Session 拿遊戲頁

拿到 Session 後，`login.js` 再請求：

```text
/logingame.aspx
```

而且會把剛才取得的 Cookie 放進 HTTP Header。

伺服器回傳的內容被當成 `swfURL` 回傳。

所以現在的流程是：

```text
帳號 + 密碼
      ↓
checkuser.ashx
      ↓
ASP Session Cookie
      ↓
logingame.aspx
      ↓
SWF / 遊戲入口資料
```

## 2.4 真正的遊戲連線從這裡開始

拿到 Flash 遊戲後，Flash 客戶端才開始做真正的遊戲通訊。

後面的遊戲操作不是靠 Axios，也不是靠 PHP；而是走遊戲本身的 TCP 封包系統。

# 第三章：Electron 客戶端在做什麼

`ClientWeb/main.js` 可以用一句話理解：

> **把舊 Flash 遊戲包成一個可以直接開啟的桌面程式。**

## 3.1 為什麼有 Express

程式開了一個 Express：

```text
localhost:9284
```

它把 `public/` 當成靜態網站根目錄。

這樣 Electron 不必直接從檔案系統打開頁面，而是像開普通網站一樣載入：

```text
http://localhost:9284
```

## 3.2 為什麼要載入 pepflashplayer.dll

因為這個客戶端依賴 Flash Player。

程式明確指定：

```text
ppapi-flash-path = flash/pepflashplayer.dll
ppapi-flash-version = 29.0.0.171
```

也就是說，這個客戶端不是使用現代瀏覽器的 HTML5 遊戲引擎，而是在 Electron 裡面掛舊式 Flash 外掛。

## 3.3 Electron 只負責外殼

真正的遊戲邏輯主要不在 `main.js`。

`main.js` 主要負責：

```text
啟動
 ↓
開 HTTP 靜態服務
 ↓
載入 Flash
 ↓
建立視窗
 ↓
把登入 IPC 接出去
```

玩家在遊戲裡打怪、射擊、進房間、聊天等動作，真正重要的處理會進入 Flash 與 Game.Server 的封包系統。

# 第四章：網頁與 Flash 在做什麼

## 4.1 Web 和遊戲伺服器不是同一件事

這個專案裡至少有兩種「伺服器」概念：

### 網站伺服器

負責：

- 登入。
- 註冊。
- 網站頁面。
- Flash 啟動所需資料。
- 一些舊式 HTTP API。

### 遊戲伺服器

負責：

- 玩家連線。
- 遊戲封包。
- 房間。
- 戰鬥。
- 玩家狀態。
- 道具。
- 任務。
- 公會。
- 排名。
- 各種遊戲規則。

兩者不要混在一起。

## 4.2 Flash 需要知道遊戲伺服器在哪

Flash 客戶端本身並不是「網站」。

它需要知道：

```text
我現在登入的是誰？
我要連哪一個遊戲頻道？
我要把遊戲封包送去哪個 IP/Port？
```

這也是為什麼 Web、Center.Server、Game.Server 之間會互相配合。

## 4.3 crossdomain.xml

`Web/crossdomain.xml` 是 Flash 時代很常見的跨網域設定。

簡單說，它是在告訴 Flash：

> 其他來源的 Flash，可以按照這份規則來連這個服務。

因此它是「讓舊 Flash 網路通訊可以成立」的一部分。

# 第五章：遊戲伺服器是怎麼接住玩家的

最核心的入口是：

```text
Source Server/Game.Server/Server/GameServer.cs
```

但 `GameServer` 並不是從零開始處理 TCP。

它繼承：

```text
GameServer
   ↓
BaseServer
```

所以要先看 `BaseServer`。

## 5.1 BaseServer：最基本的 TCP 伺服器

`BaseServer` 做的事很簡單：

1. 建立 TCP Socket。
2. 綁定 IP 和 Port。
3. 開始 Listen。
4. 有人連進來時，建立一個 Client。
5. 把 Client 放進 `_clients`。
6. 開始收資料。
7. Client 離線時，把 Client 從清單拿掉。

可以想成：

```text
Internet
   │
   ▼
TCP Socket
   │
   ▼
BaseServer
   │
   ├── Client A
   ├── Client B
   ├── Client C
   └── ...
```

## 5.2 GameServer 把「普通 Client」換成「GameClient」

`GameServer.GetNewClient()` 不會建立普通 `BaseClient`，而是：

```text
new GameClient(...)
```

所以：

```text
BaseServer
   ↓
GetNewClient()
   ↓
GameClient
```

從這裡開始，這個 TCP 連線才真正變成「一個遊戲玩家的連線」。

# 第六章：一個封包是怎麼走完整條路

這是整個專案最重要的閱讀主線之一。

假設玩家在遊戲裡按了一個按鈕。

## 6.1 Flash 送出資料

Flash 把遊戲動作轉成遊戲協定的封包。

封包進入 TCP。

```text
Flash
 ↓
TCP
 ↓
GameServer 的 Socket
```

## 6.2 BaseServer 把連線交給 GameClient

`BaseServer` 接到 Socket 後：

```text
Socket
 ↓
GameClient
 ↓
ReceiveAsync()
```

`GameClient` 繼承 `BaseClient`，所以實際收資料的底層工作在 `BaseClient`。

## 6.3 BaseClient 收到 bytes

`BaseClient.ReceiveAsync()` 使用 `SocketAsyncEventArgs`。

資料到了之後：

```text
RecvEventCallback
 ↓
OnRecv(num_bytes)
```

而 `GameClient.OnRecv()` 最後會把資料交給：

```text
StreamProcessor.ReceiveBytes()
```

## 6.4 StreamProcessor 找出完整封包

`StreamProcessor` 不假設一次 TCP Receive 就是一個完整封包。

這一點非常重要。

因為 TCP 是「資料流」，可能發生：

```text
一次收到半個封包
```

也可能：

```text
一次收到兩個封包
```

所以 `StreamProcessor` 會把 bytes 暫存在 buffer 裡，再自己找封包邊界。

## 6.5 找到完整封包後建立 GSPacketIn

找到完整資料後：

```text
byte[]
 ↓
GSPacketIn
 ↓
ReadHeader()
 ↓
GameClient.OnRecvPacket()
```

## 6.6 GameClient 第一次收到封包時建立 PacketProcessor

`GameClient.OnRecvPacket()` 發現 `m_packetProcessor == null` 時，會建立：

```text
IPacketLib
PacketProcessor
```

其中 `AbstractPacketLib.CreatePacketLibForVersion(1, this)` 會依版本建立封包讀寫工具。

## 6.7 PacketProcessor 找真正的 Handler

`PacketProcessor` 有一個固定大小的 Handler 陣列：

```text
m_packetHandlers[512]
```

收到封包後：

```text
封包 Code
   ↓
m_packetHandlers[Code]
   ↓
找到對應 Handler
   ↓
HandlePacket(client, packet)
```

所以玩家的一個動作，最後會落到一個非常具體的 `IPacketHandler` 類別。

## 6.8 Handler 才是「這個動作真正做什麼」的地方

例如玩家做的是：

```text
強化裝備
```

最後會找到對應的封包 Handler。

Handler 再呼叫：

```text
玩家物件
 ↓
Manager / Service / Bussiness
 ↓
資料庫或遊戲世界
```

這才是完整的遊戲動作。

# 第七章：封包裡的資料怎麼讀寫

`PacketIn` 是非常重要的底層工具。

它把「一堆 byte」變成程式可以直接讀的資料。

## 7.1 常見讀法

它提供：

- `ReadByte()`
- `ReadBoolean()`
- `ReadShort()`
- `ReadInt()`
- `ReadUInt()`
- `ReadLong()`
- `ReadFloat()`
- `ReadDouble()`
- `ReadString()`
- `ReadDateTime()`
- `ReadBytes()`

例如：

```text
封包
 ↓
ReadInt()
 ↓
得到玩家 ID
```

## 7.2 寫回封包

也有對應的：

- `WriteByte()`
- `WriteBoolean()`
- `WriteShort()`
- `WriteInt()`
- `WriteLong()`
- `WriteFloat()`
- `WriteDouble()`
- `WriteString()`
- `WriteDateTime()`

所以：

```text
伺服器要告訴玩家一件事
        ↓
建立 GSPacketIn
        ↓
Write...
        ↓
WriteHeader()
        ↓
SendTCP()
```

## 7.3 字串不是直接放進去

`WriteString()` 會先寫長度，再寫 UTF-8 bytes，最後補一個 `0`。

讀取時則先讀長度，再按照 UTF-8 解出文字。

所以玩家名稱、聊天文字等資料都有固定的封包格式。

# 第八章：封包加密與拆包

這是最容易讓第一次讀程式的人迷路的地方。

## 8.1 TCP 不等於一個封包

假設玩家送：

```text
封包 A
封包 B
```

TCP 可能變成：

```text
[A的一半][A剩下][B]
```

或者：

```text
[A][B的一半]
```

因此 `StreamProcessor.ReceiveBytes()` 會一直累積資料。

## 8.2 封包有自己的頭

程式會尋找固定的封包開頭。

解密後，它檢查前兩個 byte 是否等於：

```text
29099
```

也就是 `0x71AB`。

接著讀後面的長度欄位。

因此概念上可以想成：

```text
[封包標記][封包長度][封包內容...]
```

## 8.3 長度不合理就會出事

程式會檢查封包長度是否在合理範圍。

目前程式看到的上限是：

```text
8192 bytes
```

如果格式不對，而且 Client 是 Strict 模式，連線會被斷掉。

## 8.4 加密 Key

`StreamProcessor` 裡有一組 8 bytes 的初始 Key。

Client 建立 `StreamProcessor` 時，會複製這組 Key 成為自己的：

```text
RECEIVE_KEY
SEND_KEY
```

也就是收、送各自維護一份狀態。

## 8.5 解密不是單純 XOR

程式裡的解密會：

1. 使用目前 Key。
2. 依前一個 byte 更新 Key。
3. 再做 XOR 與減法。
4. 還原出原本的資料。

因此不要把它想成普通的「每個 byte XOR 固定數字」。

它會隨著資料繼續往後走而改變。

## 8.6 傳送方向也會做相對應處理

`SendTCP()` 把封包丟進 TCP Queue。

`StreamProcessor.AsyncTcpSendCallback()` 會逐個處理 Queue 裡的封包。

如果 `Encryted == true`，它會走 `PacketIn.CopyTo3()`，依 `SEND_KEY` 做編碼。

所以整條路是：

```text
收到：
TCP bytes
 ↓
解密
 ↓
找標記
 ↓
找長度
 ↓
GSPacketIn
 ↓
Handler

送出：
Handler / Game logic
 ↓
GSPacketIn
 ↓
WriteHeader
 ↓
Queue
 ↓
加密/編碼
 ↓
TCP
 ↓
Flash
```

# 第九章：登入之後，玩家在伺服器裡是什麼

`GameClient` 裡有一個非常重要的欄位：

```text
GamePlayer m_player
```

可以把它理解成：

```text
GameClient = 網路連線
GamePlayer = 這條連線背後的遊戲角色
```

剛連線時可能只有：

```text
GameClient
   │
   └── Player = null
```

登入成功後才變成：

```text
GameClient
   │
   └── GamePlayer
         ├── 角色資料
         ├── 道具
         ├── Buff
         ├── 房間狀態
         ├── 戰鬥狀態
         └── 其他遊戲資料
```

## 9.1 玩家離線

`GameClient.OnDisconnect()` 會做幾件重要事情：

1. 取出目前 `GamePlayer`。
2. 清理 FightBag。
3. 從登入管理中清掉玩家。
4. 呼叫玩家的 `Quit()`。
5. 把讀取 buffer 放回 Server 的 buffer pool。
6. 把送出 buffer 放回 Server 的 buffer pool。

所以「玩家斷線」不是只有 Socket 關掉。

它還需要把遊戲世界裡的玩家狀態一起清理。

# 第十章：遊戲世界、房間與戰鬥

Game.Server 裡可以看到幾個很重要的世界級元件：

```text
WorldMgr
RoomMgr
GameMgr
BattleMgr
```

可以先用白話理解：

## 10.1 WorldMgr

管理「整個伺服器世界裡有哪些玩家、世界資料現在怎樣」。

`GameServer` 的定時保存、Buff 掃描等工作都會走到 WorldMgr。

例如：

```text
WorldMgr.GetAllPlayers()
```

就是拿目前世界上的玩家。

## 10.2 RoomMgr

管理遊戲房間。

`GameServer.Start()` 會用：

```text
RoomMgr.Setup(MaxRoomCount)
```

啟動時建立房間系統。

之後又會：

```text
RoomMgr.Start()
```

停止時則：

```text
RoomMgr.Stop()
```

## 10.3 GameMgr

比較接近「遊戲本身的運轉管理」。

它會在 Server 啟動流程中 Setup，之後 Start。

## 10.4 BattleMgr

戰鬥相關的總管理器。

啟動順序中會先 `BattleMgr.Setup()`，之後正式 `BattleMgr.Start()`。

因此可以把它們先想成：

```text
WorldMgr = 世界
RoomMgr  = 房間
GameMgr  = 遊戲流程
BattleMgr = 戰鬥
```

這只是閱讀上的白話對照，真正細節仍在各自的類別裡。

# 第十一章：中心伺服器為什麼存在

這個專案不是只有一台 Game.Server。

它還有：

```text
Center.Server
```

而 Game.Server 會連到 Center Server。

## 11.1 GameServer 啟動時會登入 Center

`GameServer.InitLoginServer()` 會建立：

```text
LoginServerConnector
```

然後使用設定裡的：

- `LoginServerIp`
- `LoginServerPort`
- `ServerID`
- `ServerName`

連到中心伺服器。

目前設定類別的預設值中，中心 Port 是 `9202`。

## 11.2 為什麼不讓 Game.Server 自己知道全部事情

因為一個 DDTank 伺服器可能有：

```text
多個遊戲頻道
多個 Game Server
多個玩家
```

Center Server 可以當中間人。

例如：

```text
Game Server A ─┐
               │
Game Server B ─┼── Center Server
               │
Game Server C ─┘
```

這樣跨頻道的玩家、訊息、公會、世界活動等資料，就有一個共同的地方交換。

## 11.3 Center Server 也管理 Game Server 的狀態

`ServerClient` 裡可以看到：

- Server 登入。
- Server Ping。
- Online 人數。
- Server State。
- 玩家上線/離線。
- 私人訊息轉送。
- 全體廣播。
- 世界 Boss 資料。
- 公會 Boss 資料。
- 部分活動同步。

所以 Center Server 不是普通的網站 API。

它本身也是一個 TCP / 封包系統。

# 第十二章：資料庫到底扮演什麼角色

資料庫不是單純拿來登入。

它承擔的是「長期保存遊戲資料」。

玩家在線上時，很多資料可以在記憶體裡跑得很快。

例如：

```text
玩家目前 HP
玩家目前房間
玩家目前 Buff
玩家正在戰鬥
```

但玩家下線後，這些資料不能全部消失。

因此會有：

```text
記憶體
  ↓
Save
  ↓
資料庫
```

## 12.1 GameServer 的定時保存

`GameServer.InitGlobalTimer()` 會建立多個 Timer。

其中資料庫保存時間來自：

```text
DBSaveInterval
```

預設是 5 分鐘。

到時間後 `SaveTimerProc()` 會：

1. 取得所有玩家。
2. 保存玩家新聞等資料。
3. 更新 Caddy 排名。
4. 掃描商店免費有效期。
5. 掃描公會任務。
6. 清理過期的師徒請求。
7. 最後發出 `WorldSave` 事件。

## 12.2 SQL Server

從 `.BAK` 備份與 `SqlDataProvider`、`Bussiness` 等專案可以確認，這套舊系統是以 SQL Server 為重要資料來源。

所以 README 提到的「未來 SQLite」是現代化方向，不代表目前舊版 Game.Server 已經改成 SQLite。

# 第十四章：伺服器啟動時到底做了多少事

`GameServer.Start()` 是閱讀整個專案的第二條大主線。

它不是「開 Port 然後結束」。

它會按順序把整個遊戲世界準備起來。

## 14.1 先處理例外與基本設定

啟動時會：

- 設定未處理例外事件。
- 設定執行緒優先權。
- 更新 GameProperties。
- 編譯/載入 Script。
- 初始化公會等級資料。
- 載入 Script Components。
- 檢查 Edition。

## 14.2 建立 TCP Socket

接著：

```text
InitSocket(IP, Port)
```


```text
MaxClientCount × 3
```

準備 8192 bytes 的 buffer。

預設 `MaxClientCount` 是 2000，因此預設會準備約：

```text
6000 個 buffer
```

這是為了減少玩家每次連線都重新建立 byte array 的成本。

## 14.4 初始化遊戲資料

接下來會依序啟動大量元件，包括：

## 14.5 建立全域 Timer

接著設定：

- 資料庫保存 Timer。
- Ping Timer。

也就是玩家真正可以連進來的時間點。

# 第十五章：伺服器平常一直在做什麼

Server 開起來後，不是什麼都不做。

它會一直跑 Timer。

## 15.1 Ping

`PingCheck()` 會巡視所有 Client。

對已登入玩家：

```text
SendPingTime()
```

對沒有完成玩家建立、又長時間沒有回應的 Client：

```text
Disconnect()
```

同時也會 Ping Center Server。

預設 Ping 間隔是 5 分鐘。

## 15.2 Buff 掃描

`BuffScanTimerProc()` 會：

```text
WorldMgr.GetAllPlayers()
       ↓
每個玩家的 BufferList.Update()
```

所以玩家身上的 Buff、時間型效果等，需要定期被檢查。

## 15.3 Database Save

定期把需要保存的東西寫入資料庫。

## 15.4 Record Save

`SaveRecordProc()` 會呼叫：

```text
LogMgr.Save()
```

把統計/紀錄類資料保存下來。

## 15.5 世界事件

保存完成後會發：

```text
GameServerEvent.WorldSave
```

這表示「一次世界保存週期完成了」。

其他系統如果有掛這個事件，就可以在這個時間點做自己的事情。

# 第十六章：伺服器停止時發生什麼

停止也不是直接 Kill Process。

## 16.1 正常 Shutdown

`GameServer.Shutdown()` 會先通知 Center Server：

```text
SendShutdown(true)
```

然後啟動一個每分鐘跑一次的 Timer。

## 16.2 通知玩家

每次 Timer 跑，會：

1. 倒數時間減 1。
2. 在 Console 顯示剩餘時間。
3. 對所有 Client 發送 GM Notice。

當倒數結束：

```text
Center Server：停止狀態
↓
關掉 Shutdown Timer
↓
GameServer.Stop()
```

## 16.3 Stop 做清理

`Stop()` 會：

- 更新婚姻房間離線資料。
- 停止 RoomMgr。
- 停止 GameMgr。
- 停止 WorldMgr。
- 停止 ConsortiaTaskMgr。
- 斷開 Center Server。
- 停止 Ping Timer。
- 停止 DB Save Timer。
- 停止 Record Timer。
- 停止 Buff Timer。
- 停止 QQ Tips Timer。
- 停止 Bag/Mail 掃描 Timer。
- 呼叫 `base.Stop()`。
- 最後寫出 `Server Stopped!`。

所以停止其實是「把整個遊戲世界一層一層收掉」。

# 第十八章：README 寫的「現代化架構」與目前實際程式

這一章非常重要，因為如果不看清楚，讀者很容易誤以為專案現在已經是 Node.js + Vue + SQLite。

README 提到的方向是：

```text

├── web/
├── api/
├── db/
└── flash/
```

並描述：

```text

 ↓

 ↓
Flash / SWF
 ↓
Node.js
 ↓
SQLite
```

但目前根目錄的實際內容仍然是：

```text

Db
Request
Source Flash
Source Server
Tools
Web
```

同時根目錄的 `package.json` 與 `pnpm-workspace.yaml` 已經存在：

> **專案已經放入現代化方向的入口設定，但目前真正大量存在、而且能直接追出遊戲執行流程的核心仍然是舊 DDTank 4.1 C# / ASP.NET / Flash 架構。**

這不是好或壞的評價，只是目前程式碼的實際狀態。

# 附錄 C：一句話總結整個專案

如果只能記住一句話，就記住這句：

> **這是一套以舊 Flash 客戶端為前端、以 C#/.NET 的 Game.Server 為主要遊戲伺服器、以 Center.Server 協調多個伺服器、再透過 Bussiness / SqlDataProvider 把長期資料放進 SQL Server 的 DDTank 4.1 系統；Electron ClientWeb 則負責把舊 Flash 遊戲包成桌面程式，Web / Request 則負責登入、網站與舊式 HTTP 入口。**

整個專案真正的核心資料流可以濃縮成：

```text
玩家
  │
  ▼
ClientWeb / Web
  │
  │ 登入、Session、取得遊戲入口
  ▼
Flash
  │
  │ Game Protocol / TCP
  ▼
BaseServer
  │
  ▼
GameClient
  │
  ▼
StreamProcessor
  │
  ▼
GSPacketIn
  │
  ▼
PacketProcessor
  │
  ▼
Packet Handler
  │
  ▼
GamePlayer / Room / Battle / World / Manager
  │
  ├──────────────► Center.Server
  │
  ▼
Bussiness / SqlDataProvider
  │
  ▼
SQL Server
```

而伺服器生命週期則是：

```text
讀設定
  ↓
載入 Script
  ↓
建立 Socket
  ↓
準備 Packet Buffer
  ↓
初始化 World / Item / Room / Battle / 各種 Manager
  ↓
建立 Timer
  ↓
連 Center Server
  ↓
Start Listening
  ↓
玩家進入
  ↓
收封包 / 解封包 / 找 Handler / 執行遊戲邏輯
  ↓
定時 Ping / Save / Buff Scan / Record
  ↓
Shutdown
  ↓
清理玩家、房間、世界、Timer、Center 連線
  ↓
Server Stopped
```

## 版本說明

本書只描述目前 `main` 分支中可以從程式碼與檔案結構直接確認的行為。對於 README 提出的未來 `app/` 現代化架構，本書只解釋它與目前實際程式的差別，不把未來方向當成現在已完成的功能。

同樣地，專案中有不少程式是從既有 DLL 反編譯後形成的 C# 原始碼；因此部分命名、結構與註解可能保留反編譯痕跡。閱讀時應以「實際呼叫關係與資料流」為主，而不要只依賴類別名稱猜測。
